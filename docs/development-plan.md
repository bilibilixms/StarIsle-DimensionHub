## 二 第一阶段范围

试用目标建议为 2–5 家受邀商家、20–50 名受邀用户，用于发现流程问题。这个人数用于控制试运营规模，服务并发容量另按部署环境验证。

### 用户端

- 微信登录、退出登录、基础资料、个人中心。
- 商品列表、搜索、详情、简单规格选择、店铺主页。
- 收藏与取消收藏，收货地址管理。
- 从商品直接购买，选择数量、确认地址和运费、提交订单。
- 微信支付、订单列表和详情、取消未支付订单、查看发货信息、确认收货。
- 全额退款申请、处理结果查看和人工售后联系入口。

### 商家端

- 微信登录、受邀申请店铺、查看审核状态、维护店铺基础资料。
- 商品新增、编辑、图片上传、简单规格及价格库存配置、上下架。
- 订单列表与详情、发货、录入物流公司和单号。
- 审核退款申请、处理全额退款、查看处理状态。
- 最基础的待发货订单数、订单数和成交金额统计；明确排除未支付及已退款金额。

### 后端与运营

- 站内用户、微信身份、角色与店铺成员关系；不同 AppID 的微信身份分别记录，跨端绑定规则在第一阶段确定。
- 商家和用户的数据归属校验，尤其是商家之间的商品、订单及收货信息隔离。
- 商品、收藏、地址、订单、库存、支付、退款模块及数据库迁移。
- 对象存储接入、上传权限、文件类型和大小校验。
- 下单幂等、库存事务、超时关单、支付与退款通知、主动查单和异常补偿。
- 发货信息与微信交易要求的对接，基础交易对账及差异记录。
- 受限运营接口或工具：审核/停用商家、下架商品、查询异常订单、处理售后并保留操作记录。首版沿用现有两端，不另建完整管理网站。
- 测试环境、正式环境配置、HTTPS、日志、健康检查、备份恢复和发布回滚流程。

### 为控制首版复杂度采用的规则

| 事项 | MVP 规则 |
| --- | --- |
| 商品类型 | 普通实物现货；预售、数字商品和定制约稿留待后续 |
| 商品规格 | 单规格或单一规格维度，例如款式；复杂规格组合后续扩展 |
| 店铺 | 一个商家账号经营一家店铺，数据模型保留成员关系 |
| 购买方式 | 详情页直接购买；每单只含同一店铺的一个 SKU，可购买多件 |
| 运费 | 店铺固定运费规则，结算时由后端计算并保存快照 |
| 售后 | 首版处理全额原路退款；发货后争议由人工协商，记录处理及退款结果 |
| 发货 | 商家录入物流信息；首版不做电子面单和自动揽件 |
| 支付 | 先落实一种实际可用的接入模式，金额及收款商户由后端确定 |
| 订单状态 | 待支付、待发货、待收货、已完成、已取消；退款另有申请、处理中、成功和失败状态 |

社区发帖、评论、关注、私信、画师约稿、漫展报名、优惠券、积分、购物车、跨店合单、平台佣金分账、自动退货物流和复杂经营报表进入后续版本。任何一项提前加入，均需同步调整工作量或替换原有范围。

## 六 支付与账号是第一周的关键决策

两个小程序 AppID、真实登录条件、收款主体、支付接入权限、回调域名及对象存储都需要尽早落实。凭证通过环境配置或密钥管理机制提供，开发文档仅记录变量名和配置方法。

普通商户模式与服务商模式的收款主体及商户参数不同；服务商模式的交易资金结算到子商户账户。多家独立商户加入试用前，要根据实际经营关系和可开通产品确定接入路径。[微信支付接入模式](https://pay.wechatpay.cn/doc/v3/partner/4012081931)

本规划的支付阶段按一种已确定、具备使用权限的模式估算。若第一周确认需要服务商及子商户接入，M6 围绕该模式实现，受邀商户通过平台支持的流程接入；若只能落实单一真实经营主体的收款，则先与你明确调整试用商家范围，不能把其他独立商家的收款直接归到这个商户号。平台佣金、分账及开放式商户自动入驻另行规划。

支付完成后的状态确认、回调、主动查单、退款及对账均属于交易闭环；发货信息对接也纳入首版交付。微信支付开发指引明确要求交易类小程序按相关规范接入订单发货管理功能。[微信小程序支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)

外部权限尚未就绪时，我可以继续完成本地适配、测试替身和订单业务测试；这些成果记为开发进度，真实支付、退款及真机验收通过后才达到试用条件。

## 七 试用前验收标准

| 方面 | 必须验证的行为 |
| --- | --- |
| 正常闭环 | 商家发布商品 → 用户登录收藏 → 填地址下单 → 微信支付 → 商家发货 → 用户确认收货；双方订单状态一致 |
| 授权 | 未登录写请求被拒绝；用户不能看他人的地址与订单；商家不能操作其他店铺的数据；运营权限独立校验 |
| 订单与库存 | 库存为 5 时，并发提交 20 次独立购买请求，最多成功 5 单；重复使用同一下单幂等标识只产生一单 |
| 支付 | 伪造通知、金额或收款商户不匹配时拒绝更新；重复通知只生效一次；回调延迟或丢失可查单补偿 |
| 关单竞争 | 超时关单与支付成功同时发生时，不重复释放库存、不产生已支付却无记录的订单；异常可追踪处理 |
| 退款 | 申请、商家处理、退款通知/查询及失败重试可追踪；重复处理不重复退款；退款与订单状态一致 |
| 发货与售后 | 商家发货与用户查看一致；平台所需发货信息可同步或补报；售后联系方式和人工处理流程可用 |
| 前端 | iOS 和 Android 真机验证登录、上传、支付、订单和退款；加载、失败、空状态与重复操作均有反馈 |
| 数据与发布 | 新环境可执行迁移，密钥不进入仓库与前端；备份可恢复；应用可回滚；关键错误可从日志定位 |
| 质量 | 类型检查、两端构建、后端关键集成测试及已复现缺陷回归通过；无导致资金、库存或权限错误的未解决问题 |

外部审核等待与业务缺陷分开记录。测试替身通过、页面可展示或构建成功都分别记录其验证范围，最终试用验收必须覆盖真实环境的关键链路。
